# 事件处理协程创建分类说明

本文梳理 SPX 运行时中事件处理协程的主要创建位置，并区分：

- 长期存在的基础循环协程；
- 每次事件产生时创建的处理器协程；
- 协程创建后何时真正取得脚本执行权。

## 一、先区分两类协程

SPX 中有些协程只创建一次，负责持续等待和路由事件：

```text
游戏加载阶段
└── initEventLoop
    ├── eventLoop
    ├── inputEventLoop
    └── logicLoop
```

这些是游戏生命周期内的长期协程，不是每个输入或定时器事件都重新创建。

另一类是事件处理器协程：

```text
事件发生
└── 找到匹配的用户处理器
    └── 创建一个受管 Thread
        └── 执行 OnStart、OnClick、OnKey、OnCond 等用户代码
```

下面的分类主要讨论第二类“事件处理器协程”的创建路径。

## 二、启动事件：OnStart

OnStart 是独立的生命周期路径，不经过普通输入事件通道。

```text
BootstrapDone = true
└── runFrameScripts
    └── dispatchStartEventIfNeeded
        └── 创建启动事件分发协程
            └── 创建各个用户 OnStart 处理器协程
```

特点：

- 每局游戏只派发一次；
- 不经过 `Game.events` 和 `eventLoop`；
- 使用 `BatchWaitFirstSlice`；
- 只等待每个 OnStart 处理器执行到第一次 `Yield`、`Wait` 或结束；
- 不等待所有 OnStart 处理器完整执行完毕。

因此，OnStart 的“事件分发协程”和每个用户 OnStart 处理器是两层概念：

```text
runFrameScripts
└── 启动事件分发协程
    └── 批量创建用户 OnStart 处理器协程
```

## 三、输入和定时器事件：inputLoop/logicLoop -> eventLoop

### 3.1 输入事件

```text
gco.Update
└── 恢复 inputEventLoop
    ├── 读取鼠标、键盘状态
    ├── 生成 eventLeftButtonDown
    ├── 生成 eventLeftButtonUp
    └── 生成 eventKeyDown
        └── fireEvent
            └── 写入 Game.events 通道

eventLoop
└── WaitForChan(Game.events)
    └── 通道收到事件
        └── worker 唤醒 eventLoop
            └── handleEvent
                └── 创建 Click、Key 等处理器协程
```

这里的关系不是“inputEventLoop 直接调用 eventLoop”，而是：

```text
inputEventLoop -> Game.events 通道 -> eventLoop -> 事件处理器协程
```

`inputEventLoop` 每轮处理完成后调用 `WaitNextFrame`，通常由后续的 `gco.Update` 恢复。
`eventLoop` 通过 `WaitForChan` 等待通道；通道收到事件时，worker 可以直接唤醒它，
不要求等到下一次 `gco.Update` 才发出唤醒信号。

实时鼠标移动有一个例外：它通常直接更新 `inputMgr`，不包装成 `Game.events` 中的事件。

### 3.2 定时器事件

```text
gco.Update
└── 恢复 logicLoop
    └── 发现到期 Timer
        └── fireEvent(eventTimer)
            └── Game.events 通道
                └── eventLoop
                    └── 创建 Timer 处理器协程
```

因此，输入事件和定时器事件都属于“先进入 `eventLoop`，再创建用户处理器”的路径，
但它们的来源不同：输入来自 `inputEventLoop`，定时器来自 `logicLoop`。

## 四、条件事件：dispatchConditions

条件事件分为“采样”和“派发”两个阶段。

```text
OnEngineBeforeUpdate
└── sampleConditions
    └── 求值所有 OnCond
        └── 保存本帧命中的处理器快照

Game.OnEngineUpdate
└── dispatchConditions
    └── 创建 OnCond 处理器协程

gco.Update
└── 给这些 runnable 处理器执行机会
```

需要注意：

- `sampleConditions` 负责判断条件是否从 false 变为 true；
- `dispatchConditions` 不重新求值，只消费已经保存的快照；
- `dispatchConditions` 本身不执行用户处理器主体；
- `StartDispatched` 变为 true 之前，不会采样和派发条件事件。

## 五、物理碰撞事件：processPhysicsTriggers

物理触发事件不经过 `Game.events` 和 `eventLoop`。

```text
Godot 物理回调
└── 记录 pending 触发事件

下一次 onUpdate 开始
└── pending -> ready

Game.OnEngineRender
└── processPhysicsTriggers
    └── 消费 ready 触发事件
        └── fireTouchStart
            └── 创建 OnTouchStart 处理器协程
```

物理回调现场只记录源对象和目标对象，用户的 OnTouchStart 不在物理回调栈中直接执行。
`processPhysicsTriggers` 使用 `BatchAsync` 登记/启动匹配的处理器。

## 六、已经运行的用户协程内部创建新协程

用户脚本本身已经运行在受管协程 A 中时，部分 API 会在 A 的执行过程中创建新的事件
处理器协程 B。

### 6.1 Broadcast

```text
用户脚本协程 A
└── Broadcast("hello")
    └── doWhenIReceive
        └── dispatchGlobal
            └── StartBatch
                └── 创建消息处理器协程 B
```

普通 `Broadcast` 使用 `BatchAsync`，A 不等待 B。`BroadcastAndWait` 使用
`BatchWaitDone`，A 会等待所有匹配的消息处理器完成。

### 6.2 SetBackdrop

```text
用户脚本协程 A
└── SetBackdrop(...)
    └── setBackdrop
        └── doWhenBackdropChanged
            └── dispatchGlobal
                └── StartBatch
                    └── 创建 OnBackdrop 处理器协程 B
```

普通 `SetBackdrop` 不等待，`SetBackdropAndWait` 等待处理器完成。

### 6.3 Clone 和 OnCloned

```text
用户脚本协程 A
└── Clone()
    ├── 创建克隆对象和 Godot 代理
    ├── 执行克隆 awake
    ├── 在当前 Clone 调用流程中执行克隆 Main
    │
    └── dispatchCloneLifecycle
        └── doWhenCloned
            └── 创建 OnCloned 处理器协程 B
```

这里要区分：

- 克隆的 `Main` 不是新建的 OnCloned 协程，它在 Clone 当前调用流程中执行；
- `OnCloned` 才是额外创建的独立协程；
- `OnCloned` 使用 `BatchWaitFirstSlice`；
- Clone 只等待 OnCloned 处理器首次挂起或结束，不等待它完整执行完。

这些协程在逻辑上由用户协程 A 发起，但在调度器中是独立的受管 Thread，
不是 Go 调用栈意义上的嵌套协程。

## 七、批处理模式和执行时机

“创建协程”不等于“处理器主体已经执行”。事件分发使用不同的批处理模式：

```text
BatchAsync
└── 只登记任务，不等待处理器取得执行权

BatchWaitFirstSlice
└── 等每个处理器首次 Yield、Wait 或结束

BatchWaitDone
└── 等所有处理器彻底结束
```

因此不能简单概括为“所有新协程都等下一次 `gco.Update` 才运行”：

```text
处理器创建
├── 当前调度器仍在运行且 runMu 可用
│   └── 可能立即执行第一段
│
├── 处理器调用 WaitNextFrame 或时间等待
│   └── 后续部分由后续 gco.Update 恢复
│
├── 处理器调用 WaitForChan
│   └── 由通道 worker 直接唤醒，不严格依赖 gco.Update
│
└── 处理器调用 YieldLoop
    ├── 预算允许且没有请求重绘
    │   └── 可能在同一个 gco.Update 中进入下一轮
    └── 否则延期到下一次 gco.Update
```

## 八、统一分类图

```text
事件处理协程创建点
├── 生命周期路径
│   └── OnStart
│
├── 帧循环路径
│   ├── inputLoop
│   └── logicLoop
│       └── eventLoop 创建输入/定时器处理器
│
├── GameUpdate 路径
│   └── dispatchConditions 创建 OnCond 处理器
│
├── GameRender 路径
│   └── processPhysicsTriggers 创建 OnTouchStart 处理器
│
└── 用户脚本路径
    ├── Broadcast
    ├── SetBackdrop
    └── Clone -> OnCloned
```
