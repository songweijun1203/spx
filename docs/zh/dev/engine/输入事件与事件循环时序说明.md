# 输入事件与事件循环时序说明

## 说明范围

本文整理 SPX 中输入事件从 Godot 回调进入 Go，到高层事件路由和用户协程启动的时序。
重点说明以下对象之间的关系：

- Godot 输入回调；
- `pending` / `ready` 输入缓存；
- `inputEventLoop`；
- `Game.events`；
- `eventLoop`；
- `WaitForChan` 创建的 worker；
- `runnableThreads`；
- `gco.Update()` 和下一帧 `OnEngineUpdate()`。

本文也记录目前能够从代码确认的语义，以及仍然需要项目设计明确的问题。文中的“输入事件”
主要指键盘和鼠标事件；碰撞、条件、广播和克隆事件会在后面单独说明。

## 先给结论

SPX 当前不是单一的“所有事件都由帧循环处理”模型，而是混合模型：

```text
底层输入接入：事件驱动
输入快照建立：帧驱动
普通高层事件路由：Game.events + 异步 eventLoop
用户协程执行：受 runMu 和协程调度器控制
```

因此需要区分四个时间点：

```text
输入发生的时间
    ↓
输入被 Go 接收的时间
    ↓
输入被纳入 pending/ready 帧快照的时间
    ↓
高层事件被 eventLoop 路由、用户处理器取得执行权的时间
```

这四个时间点不一定相同。

当前代码能够保证：

- 输入回调不会直接在 Godot 原始回调栈中执行完整用户处理器；
- 键盘等边沿事件可以在帧边界从 `pending` 转移到 `ready`；
- `eventLoop` 的 `handleEvent` 在取得受管协程的 `runMu` 后执行；
- 已经发布为 `runnable` 的受管协程不会被调度器完全忽略。

当前代码不能直接保证：

- 一个输入事件一定在采样它的同一帧完成高层事件路由；
- 一个已经进入 `Game.events` 的事件一定在当前 `gco.Update()` 返回前处理；
- 用户处理器读取到的一定是事件发生时的场景状态；
- 事件队列在高负载下永远不丢事件；
- `eventLoop` 与下一帧 `OnEngineUpdate` 之间具有完整的全局帧锁。

## 一帧的外层顺序

`internal/engine/engine.go:onUpdate` 是 Go 侧普通逻辑帧入口。核心顺序如下：

```text
Godot 每帧调用 Go OnEngineUpdate
        ↓
cacheTriggerEvents()
cacheKeyEvents()
cacheMouseEvents()
        ↓
OnEngineBeforeUpdate()
        ↓
推进 SPX 逻辑时间
        ↓
OnEngineUpdate()
        ↓
gco.Update()
        ↓
OnEngineRender()
        ↓
截图/捕获队列处理
        ↓
OnEngineFrameEnd()
```

对应实现位置：

- `internal/engine/engine.go:177`：`onUpdate` 总流程；
- `internal/engine/engine.go:194`：输入和触发事件的帧边界缓存；
- `internal/engine/engine.go:208`：`OnEngineUpdate`；
- `internal/engine/engine.go:215`：`gco.Update`；
- `internal/engine/engine.go:222`：`OnEngineRender`。

这里的 `gco.Update()` 不是“所有协程的唯一执行入口”。它主要处理调度器中的 `WaitJob`，
例如 `Wait`、`WaitNextFrame` 和可在当前更新中处理的脚本轮次。`WaitForChan` 使用的
外部 worker 不登记 `WaitJob`，因此可以绕过下一次 `gco.Update()` 直接恢复原协程。

## 输入回调阶段：只记录状态或写入 pending

### Native 路径

Godot 的 `SpxInputProxy::input` 接收 Viewport 传播的键盘、鼠标事件，并同步调用 Go 回调：

```text
操作系统输入
    ↓
Godot Viewport
    ↓
SpxInputProxy::input
    ↓
func_on_key_pressed / func_on_mouse_pressed
    ↓
Go 输入状态函数
```

实现位置：`godot_modules/spx/spx_input_proxy.cpp:59`。

键盘事件进入 `queueKeyEvent`：

```go
keyInput.pending = append(keyInput.pending, KeyEvent{...})
```

实现位置：`internal/engine/input_state.go:123-145`。

鼠标回调会立即更新原子按住状态：

```go
mouseInput.buttons[id].Store(pressed)
```

同时，去重后的按下/抬起边沿总会写入 `mouseInput.pending`。原子状态供即时查询，
`pending/ready` 队列则保留同一帧内的真实边沿顺序；实时输入循环和输入会话共享这套队列，
并由上层保证每帧只有一个消费者。

### Web 路径

Web 使用统一的 `gdspxDispatch` 接收 JavaScript/Godot 侧事件，再调用 Go 回调表：

```text
JavaScript/Godot
    ↓
gdspxDispatch
    ↓
OnKeyPressed / OnMousePressed
    ↓
Go 输入状态函数
```

实现位置：`internal/gdengine/binding/web/callbacks.gen.go:217-242`。

Web 回调通常在 JavaScript 主线程同步执行。JavaScript 事件本身不会在当前同步回调尚未返回
时再次插入执行，但事件可以排队到后续回调；这与 Go 侧 worker 的调度问题是两个层次。

## `pending → ready`：帧边界快照

在 `onUpdate` 开始处：

```text
pending：已经到达 Go、但尚未归入某个帧快照的事件
    ↓ cache
ready：本帧允许输入循环消费的事件
```

键盘缓存由 `cacheKeyEvents` 完成，鼠标缓存由 `cacheMouseEvents` 完成，碰撞触发缓存由
`cacheTriggerEvents` 完成。

它的主要意义是建立帧边界：

```text
cache 之前到达的事件：有机会归入本帧 ready
cache 之后到达的事件：留在 pending，下一次 cache 再处理
```

但 `ready` 只定义了“底层事件属于哪一次输入快照”。它并不自动保证：

```text
ready 中的事件一定在本帧完成 eventLoop 路由
```

## `inputEventLoop`：把输入状态转换为高层事件

`inputEventLoop` 是一个长期受管协程，主体位于 `runtime_loops.go:45`，底层循环位于
`internal/core/runtime/loop.go:156`。

每一轮大致执行：

```text
等待下一帧
    ↓
读取当前鼠标位置
    ↓
读取本帧 ready 鼠标边沿和最终按住状态
    ↓
读取本帧 ready 键盘边沿
    ↓
比较上一帧/当前帧状态
    ↓
生成 eventLeftButtonDown / eventLeftButtonUp / eventKeyDown
    ↓
写入 Game.events
    ↓
WaitNextFrame()
```

关键点：

- `inputEventLoop` 不直接调用 `eventLoop`；
- 它通过 `p.fireEvent` 写入 `Game.events`；
- `inputEventLoop` 本身主要由 `WaitNextFrame` 通过 `gco.Update` 恢复；
- 实时鼠标位置来自当前引擎查询；按钮点击先按 `mouseInput.ready` 中的边沿顺序派发，
  再用同一帧的最终按住状态校验，以兼容旧回放和平台漏报边沿的情况。

输入转换代码位于 `internal/core/runtime/loop.go:235-297`。

## `Game.events`：另一层队列

`Game.events` 与底层输入的 `pending/ready` 不是同一个队列。

```text
底层输入队列：pending / ready
    ↓ inputEventLoop 消费
高层游戏事件队列：Game.events
    ↓ eventLoop 消费
事件注册表匹配和用户协程派发
```

`Game.events` 在 `startLoad` 中创建，默认容量为 16：

```text
game.events = make(chan event, eventBufferSize)
```

实现位置：`game_build.go:85-98`、`game.go:69`。

默认队列策略是 `DropNewest`。队列满时，新事件可能直接丢弃；`QueueBlock` 等策略也会受到
调用方是否处于受管协程的影响。相关实现位于 `internal/core/event/queue.go:141-183`。

因此必须区分：

```text
事件延迟：事件已成功进入 Game.events，但 eventLoop 尚未处理
事件丢失：事件因为队列策略没有成功进入 Game.events
```

## `eventLoop` 与 `WaitForChan`

### 初始结构

`initEventLoop` 创建的是一个受管 Thread：

```go
coreruntime.InitLoops(gco.Create, coreruntime.LoopTasks{
    Event: p.eventLoop,
    Input: p.inputEventLoop,
    Logic: p.logicLoop,
})
```

实现位置：`runtime_loops.go:27-43`、`internal/core/runtime/loop.go:220-233`。

`eventLoop` 运行 `RunEventLoop`：

```go
for {
    handle(engine.WaitForChan(events))
}
```

实现位置：`internal/core/runtime/loop.go:107-113`。

### 等待阶段

受管 `eventLoop` 调用 `WaitForChan` 后，`WaitToDo` 创建普通 worker：

```text
eventLoop
    ↓ WaitForChan
WaitToDo
    ↓
eventLoop 标记为 blocked
    ↓
eventLoop Yield，释放 runMu
    ↓
worker 在 select 中等待 Game.events
```

worker 内部等待：

```go
select {
case value = <-ch:
case <-me.Context().Done():
}
```

实现位置：`internal/coroutine/wait.go:128-155`。

这一步的意义是：eventLoop 等待外部事件时不占用脚本执行权。否则它如果直接持有 `runMu`
阻塞在 channel 上，其他用户脚本也无法继续执行。

### 事件到达后的恢复阶段

当 worker 收到事件：

```text
worker 从 select 返回
    ↓
results <- result
    ↓
markRunnableAndResume(eventLoop)
    ↓
eventLoop 从 Yield 恢复
    ↓
重新取得 runMu
    ↓
WaitForChan 返回事件
    ↓
handle(event)
```

`markRunnableAndResume` 的顺序是：

```text
先把 Thread 放入 runnableThreads
    ↓
通知 schedulerCond
    ↓
Resume 底层 Go goroutine
```

实现位置：`internal/coroutine/scheduler.go:168-182`。

`WaitForChan` 的 worker 不创建 `WaitJob`，所以 eventLoop 的唤醒不要求等待下一次
`gco.Update()`。实现注释位于 `internal/coroutine/wait.go:128-134`。

## `runnable` 状态到底保证什么

`runnable` 很容易被误解成“本帧马上执行”。它实际表示：

```text
这个受管 Thread 已经不再等待外部条件，具备继续执行的资格。
```

它不保证：

- 当前帧执行；
- 立即取得 `runMu`；
- 在当前 `gco.Update()` 返回前完成；
- 事件处理时读取到事件发生瞬间的场景状态。

它的有限作用是：如果 `eventLoop` 已经被发布为 `runnable`，并且 `gco.Update` 还在执行
调度检查，那么 `gco.Update` 不会把调度器误判为空闲。

```text
gco.Update 检查 runnableThreads
    ↓
发现 eventLoop runnable
    ↓
等待 eventLoop 执行到下一次 WaitForChan 或结束
```

这是一种“调度器空闲判断屏障”，不是帧同步机制。

## 三种关键时序

### 情况一：事件在当前 `gco.Update` 中发布为 runnable

```text
gco.Update 正在运行
    ↓
worker 收到 Game.events
    ↓
eventLoop 被标记 runnable
    ↓
gco.Update 发现 runnable
    ↓
等待 eventLoop 处理并重新 WaitForChan
    ↓
gco.Update 返回
    ↓
进入渲染前阶段
```

此时 `runnable` 有实际作用：它可以避免一个已经被调度器发现的 eventLoop 越过当前
`gco.Update` 的尾部。

### 情况二：事件在 `gco.Update` 返回后才发布

```text
gco.Update 检查时 eventLoop 仍为 blocked
    ↓
gco.Update 返回
    ↓
worker 才收到事件，或才得到 Go 调度时间
    ↓
eventLoop 被标记 runnable
    ↓
eventLoop 执行 handleEvent
```

本次 `gco.Update` 已经没有机会等待它。此时 eventLoop 可能在两次帧回调之间执行，
也可能延迟到下一帧之后。

在 eventLoop 已经执行完并重新进入 `WaitForChan` 的情况下，状态可能只是：

```text
blocked → runnable → blocked
```

而期间没有任何 `gco.Update` 读取到它。对这个具体时序，`runnable` 没有可见效果。

### 情况三：eventLoop 延迟到下一帧更新期间

理论上可能出现：

```text
第 N 帧 gco.Update 返回
    ↓
第 N+1 帧 OnEngineUpdate 开始修改场景状态
    ↓
worker 才发布 eventLoop runnable
    ↓
eventLoop 执行上一批输入事件
```

这时 `runnable` 不能撤销已经执行的 `OnEngineUpdate`，也不能把事件恢复到第 N 帧的
场景状态。若 Native 路径中 eventLoop 和帧回调运行在不同 Go goroutine，还需要进一步
核对它们访问游戏状态时是否存在并发读写风险。

因此，`runnable` 只能解决“已经发布的可运行 Thread 不被当前 Update 忽略”，不能解决
eventLoop 的帧归属和事件时序问题。

## 普通输入事件的完整修正版流程

```text
操作系统/浏览器产生输入
    ↓
Godot 输入回调
    ↓
Go 回调更新输入状态或写入 pending
    ↓
下一次 onUpdate 开始
    ↓
pending → ready
    ↓
OnEngineBeforeUpdate
    ↓
OnEngineUpdate / gco.Update 恢复 inputEventLoop
    ↓
inputEventLoop 读取 ready 边沿、按住状态快照和当前鼠标位置
    ↓
转换为 eventKeyDown / eventLeftButtonDown 等高层事件
    ↓
p.fireEvent 写入 Game.events
    ↓
WaitForChan 的 worker 接收 Game.events
    ↓
worker 发布 eventLoop runnable 并 Resume
    ↓
eventLoop 取得 runMu
    ↓
handleEvent
    ↓
匹配 OnKey / OnClick 等注册项
    ↓
gco.StartBatch 创建用户处理器协程
```

这里需要特别标注：

```text
inputEventLoop 是由 WaitNextFrame 和 gco.Update 驱动的长期协程；
eventLoop 不是由 gco.Update 直接恢复，而是由 channel worker 唤醒；
eventLoop 的用户处理器是否在当前 Update 中运行，没有严格保证。
```

## 碰撞、条件和直接事件不是同一条路径

### 条件事件

```text
OnEngineBeforeUpdate
    ↓
求值条件并保存命中的处理器快照
    ↓
OnEngineUpdate
    ↓
dispatchConditions
    ↓
创建条件处理器协程
```

条件事件不经过 `inputEventLoop` 和 `Game.events`。

### 碰撞触发事件

```text
Godot 物理回调
    ↓
trigger.pending
    ↓
onUpdate 开始时 pending → ready
    ↓
OnEngineRender
    ↓
processPhysicsTriggers
    ↓
创建 OnTouchStart 处理器协程
```

实现位置：`internal/engine/trigger_event.go:48-89`、`runtime_engine.go:154-173`。

### Broadcast、Clone、Backdrop 等直接事件

这些事件可以在已有用户协程中直接调用事件注册表：

```text
用户协程调用 Broadcast / Clone / Backdrop API
    ↓
直接匹配事件注册表快照
    ↓
gco.StartBatch
    ↓
创建对应处理器协程
```

它们不一定经过 `Game.events`，也不一定等待下一次输入帧缓存。

## 已经确认的结论

1. `inputEventLoop` 和 `eventLoop` 是并列的长期协程，不是前者直接调用后者。
2. `inputEventLoop` 主要通过 `WaitNextFrame` 由 `gco.Update` 恢复。
3. `eventLoop` 使用 `WaitForChan`，其 worker 收到事件后可以直接恢复 eventLoop，不必等待下一次 `gco.Update`。
4. `runnableThreads` 不是帧事件队列，也不是事件延迟保证；它只是调度器对已发布可运行 Thread 的记录。
5. `pending → ready` 只定义底层输入快照边界，不定义高层 `eventLoop` 的完成时刻。
6. 输入事件成功写入 `Game.events` 后，仍可能因为 worker、`runMu` 或其他调度因素延后处理。
7. `Game.events` 满时可能丢弃事件，必须把“延迟”和“丢失”区分开。
8. 如果 eventLoop 在下一帧 `OnEngineUpdate` 之后才执行，当前 `runnable` 机制不能恢复事件发生时的场景快照。

## 仍需明确的设计问题

### 1. SPX 对普通输入的正式时序承诺是什么？

需要明确选择以下哪一种：

```text
A. 事件驱动语义：事件最终处理即可，不保证同帧
B. 帧驱动语义：事件按输入快照归属帧，并在明确阶段派发
```

当前实现更接近 A，但 `pending/ready` 和 `OnUpdate` 的结构又表现出 B 的意图。

### 2. eventLoop 是否允许与下一帧 OnEngineUpdate 并发访问游戏状态？

`runnableThreads` 只被调度器更新阶段使用，不能自动保护 `OnEngineUpdate` 的前置阶段。
需要确认 Native 路径下 eventLoop 和主帧回调的线程约束，以及 `handleEvent` 访问的精灵、
输入和注册表状态是否有独立锁或只允许在特定线程访问。

### 3. 点击等事件需要读取事件发生时的状态，还是处理时的当前状态？

当前点击事件保存了鼠标位置，但目标命中检测在 `handleEvent` 执行时进行。如果事件跨帧，
精灵可能已经移动、隐藏或销毁。需要明确这是有意的“处理时状态”，还是应该在输入采样时
保存更完整的事件快照。

### 4. 输入队列是否允许丢事件？

默认 `DropNewest` 表明队列过载时允许丢失，但键盘按下、点击和物理事件的可丢失性可能不同。
需要按事件类别确认队列容量和策略，而不是只看统一的 `Game.events` 配置。

### 5. Web 和 Native 是否要求相同的处理时序？

Web 通常受 JavaScript 单线程事件循环限制，Native 则存在 Go worker 与 Godot 主线程的
并行可能。若两者要有相同的脚本语义，需要额外的帧门控或统一事件快照。

## 两种可选设计方向

### 保留当前异步事件模型

```text
worker 等待事件
    ↓
eventLoop 直接异步恢复
    ↓
受 runMu 保护执行 handleEvent
```

需要补充明确的设计契约：

- 事件只保证最终处理，不保证同帧；
- 事件处理器读取的是处理时状态；
- 明确 Native 并发访问的保护方式；
- 监控并暴露队列丢弃统计；
- 对需要事件时状态的事件保存不可变快照。

### 改为严格帧驱动事件模型

```text
Godot 回调 / worker
    ↓
只写入 pending
    ↓
OnUpdate 建立 ready 高层事件快照
    ↓
gco.Update 统一派发
    ↓
用户处理器协程执行
```

这种模型更容易保证事件与帧的归属和顺序，但会引入至少一个明确的帧阶段延迟，且不再具备
当前 `WaitForChan` 直达 eventLoop 的低延迟特征。

## 最终认识

SPX 当前的核心结构可以概括为：

```text
事件驱动接入
    + 帧驱动输入采样
    + 异步 channel 事件循环
    + 受管协程执行
```

其中最容易混淆的是：

```text
输入被某一帧采样
不等于
eventLoop 在这一帧执行
不等于
用户处理器在这一帧完成
```

`runnable` 只是在事件循环已经被调度器发现时，帮助 `gco.Update` 判断是否仍有未完成的
受管执行片段；它不能把异步 eventLoop 重新变成严格的帧驱动循环。
